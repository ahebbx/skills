# 目标推进

把用户的整体目标变成能落地的推进方案，并随进度持续优化。核心思路：**先问清目标 → 补全关键路径 → 按优先级和真实精力排期 → 记录进度 → 用历史数据校准下一轮**。技能本身是通用的，差异化全部来自用户的本地记录——记录越多，估时越准、排期越贴合。

## 数据文件（存放路径要求，必须遵守）

所有数据**只能**存放在固定路径 `~/.goal-planner/` 下。该路径独立于任何 agent 工具（Cursor、Claude Code、Codex 等），无论从哪个工具、哪个项目触发本 skill，都读写同一份数据。Windows 上 `~` 即 `C:\Users\<用户名>`；文件一律 UTF-8 编码读写。

```
~/.goal-planner/
├── profile.md          # 用户画像 + 精力 + 执行规律（差异化的核心）
├── plan.md             # 跨所有目标的当前推进方案：精力分配 + 本周任务
├── log.md              # 进度日志，最新在最上面，只追加
├── goals/<slug>.md     # 每个整体目标一份：目标定义、子目标、里程碑
└── archive/            # 已完成 / 已放弃的目标
```

规则：

1. 目录不存在时先创建（macOS/Linux：`mkdir -p ~/.goal-planner/goals ~/.goal-planner/archive`；Windows PowerShell：`New-Item -ItemType Directory -Force ~/.goal-planner/goals, ~/.goal-planner/archive`）。
2. 禁止把数据写到其他位置（skill 自身目录、项目目录、临时文件等）。
3. `log.md` 只追加、不删改历史条目；修正错误时新增一条更正记录。
4. `goals/<slug>.md` 和 `plan.md` 改版时版本号 +1 并写修改日期，不另建新文件。`<slug>` 用简短英文或拼音，如 `ai-pm-transition.md`。
5. 文件损坏/读不出：不要清空。提示用户，先复制为 `<文件名>.bak` 再重建。
6. 无文件系统的环境（如网页聊天）：跳过读写，只在对话内完成规划，并提醒用户自己保存方案。

## 工作流程

**每次触发，先用命令行取当前日期和星期（macOS/Linux：`date`；Windows PowerShell：`Get-Date`），再读取 `profile.md`、`plan.md`、`log.md` 最近 20 条左右、以及相关的 `goals/*.md`（存在的话），然后决定走哪个分支：**

- **没有 profile.md** → 首次使用，先「建档」，再接着处理用户的请求
- **用户提出新目标 / 想重新规划** → 「新目标」
- **用户汇报进度、完成、卡住、没时间** → 「记录进度」
- **用户问今天 / 这周做什么** → 「今日任务」
- **到了复盘时机**（见下）或用户主动要复盘 → 「复盘调整」
- **用户要改目标、目标已达成或想放弃** → 「目标变更」

一次消息可能同时触发多个分支（如"A 做完了，这周还剩什么？"），按顺序都处理。

### 建档

一次问清（有提问/选项工具就用，没有就直接在回复里问），用户已经在消息里说过的不再问：

- 每周大概能投入多少小时？哪些时段可用？一天里精力最好的时候？
- 有没有固定约束（上班时间、带娃、出差等）？
- 偏好的节奏（每天一点 vs 周末集中）？

写入 `profile.md`，执行规律部分先留默认值（估时系数 1.0，待数据积累后更新）。

### 新目标

**a. 澄清——把目标问到"明确"为止**

明确目标的标准，逐条检查，缺什么问什么，一次问完：

| 要素 | 检查问题 |
|------|----------|
| 完成标准 | 怎么算达成？能否量化或给出一个可验证的结果？ |
| 截止时间 | 什么时候之前？有没有硬性节点？ |
| 为什么 | 达成后得到什么？（决定取舍时的依据） |
| 起点 | 现在已经有什么基础、做到哪一步了？ |
| 约束 | 预算、资源、不能做的事、必须用的方式？ |
| 精力 | 这个目标每周能分到多少时间？（多目标时要分配） |

用户说不清时，不要追问抽象问题，而是给 2–3 个具体化的版本让其挑选或修改。例如"想提升英语" → "A. 6 个月后雅思 7 分；B. 能不查词典读完英文技术文档；C. 能用英语完成一次 30 分钟面试"。

**b. 拆解与补全**

1. 保留用户给的子目标，不擅自删除（觉得不必要的可以说明理由，让用户决定）。
2. 从完成标准倒推关键路径，补上用户没列但达成目标必需的事项，常见几类：
   - 前置条件（资质、账号、工具、预算、他人许可）
   - 依赖与衔接（A 完成才能开始 B 的中间产物）
   - 风险验证（最不确定的假设先用小成本试一下，如"先约 2 个从业者聊聊"）
   - 资源准备（学习材料、人脉、时间腾挪）
   - 收尾交付（作品集、复盘、申请、上线等"最后一公里"）
3. 补充项标注「AI 补充」并写一句理由，请用户确认或删掉。
4. 子目标过大时继续拆，直到能估出投入时长。

**c. 排优先级**

按以下顺序排序，并标明依赖关系：

1. **P0 关键路径 / 阻塞项**：不做后面全部卡住的事、有硬截止的事
2. **P1 高风险先验证**：不确定性最大、可能推翻整个方案的假设，越早用小成本验证越好
3. **P2 高杠杆**：对完成标准贡献大、投入相对小的事
4. **P3 其余**：重要但不紧急、可以并行或延后的事

**d. 精力匹配**

1. 估算每个子目标的投入时长，再乘以 `profile.md` 里的**估时系数**（历史上实际耗时 / 预估耗时）。
2. 每周只排可投入精力的 **80%**，留 20% 缓冲给意外和超时。
3. 有多个目标时，把总精力在目标之间分配（按截止时间和重要性），写进 `plan.md` 的精力分配表。
4. 总需求超出截止前的可投入精力时，**不要硬塞**，明确告诉用户缺口多大，给 2–3 个选项让其选：砍范围（降低完成标准）、延期、增加投入、暂停其他目标。

**e. 输出与保存**

1. 展示方案：目标定义 → 子目标表（含优先级、依赖、预估投入）→ 阶段里程碑 → **本周任务**（近细远粗：本周细化到具体动作，下阶段只到里程碑）。
2. 写入 `goals/<slug>.md`，更新 `plan.md`，在 `log.md` 顶部记一条"目标启动"。

### 记录进度

1. 把用户的汇报整理成一条日志，追加到 `log.md` 顶部（格式见模板）。用户提到的实际耗时、完成情况、阻碍、感受都记下。
2. 更新 `goals/<slug>.md` 中对应子目标的状态，`plan.md` 本周任务打勾。
3. 对比计划算偏差：实际耗时 vs 预估、本周完成率。
4. 更新 `profile.md` 的执行规律（见下方「越用越懂用户」）。
5. 简短反馈：完成了什么 → 目标整体进度 → 下一步做什么。只提 1–2 个最关键的调整，不长篇大论。
6. 用户卡住时：先判断卡点类型（不知道怎么做 / 没时间 / 没动力 / 外部依赖），针对性给出拆小、换路径、调优先级或暂停的建议。
7. 推进中新发现的必要事项，作为子目标加入并标注发现日期。

### 今日任务

根据 `plan.md` 的本周任务、今天星期几、今天可用时段，把所有目标的任务合并排序，给出今天要做的 1–3 件事（P0 优先；高难度任务放在用户精力高峰时段）。每件事写清动作和完成标准。本周任务已全部完成时，从下一个里程碑提前拉任务，或建议休息。

### 复盘调整

**触发时机**：新的一周第一次触发本 skill（且上周有计划）、里程碑到期、连续两次汇报偏差明显（完成率 < 60% 或耗时超预估 50% 以上）、用户主动要求。

1. 统计上个周期：任务完成率、实际 vs 预估耗时、里程碑进展，对照截止时间判断是否在轨。
2. 调整：
   - 完成率 < 60% → 降负荷：减少每周任务数、砍范围或延期，并找出没完成的根因
   - 完成率 ≥ 90% 且耗时不超 → 可小步加量（每周增量 ≤ 20%）
   - 偏离截止时间 → 重新做精力匹配，必要时让用户在砍范围/延期/加投入中选择
3. 重排所有子目标的优先级（已完成的风险验证可能改变后续路径）。
4. 排出新一周的本周任务。
5. `plan.md` 和相关 `goals/*.md` 版本号 +1，`log.md` 记一条复盘结论（数据 + 调整了什么 + 为什么）。

### 目标变更

- **修改目标**：更新 `goals/<slug>.md`（版本 +1），重新走 b–e。
- **达成**：庆祝一下，在 log 记录达成；文件移到 `archive/`，标注达成日期；释放的精力重新分配给其他目标。
- **放弃/暂停**：问一句原因（记入 log，供以后定目标参考），文件移到 `archive/` 或标为暂停。

## 越用越懂用户（执行规律）

每次记录进度和复盘时，更新 `profile.md` 的「执行规律」，并在下次规划时**真正使用**这些数据：

- **估时系数**：累计的 实际耗时 / 预估耗时（平滑更新，如 新系数 = 0.7 × 旧系数 + 0.3 × 本次比值）。系数 1.5 意味着以后预估都要乘 1.5。
- **实际可用精力**：用户说每周 10 小时但连续几周只投入 6 小时，就按 6 小时排，并温和点出差距。
- **各类任务完成情况**：哪类任务总是完成（如输出型）、哪类总是拖（如社交型、需要联系别人的），拖的类型拆得更小或放到精力高峰。
- **常见阻碍**与**有效策略**：用户说过有用的做法（如"早上 7 点前做最难的事"）记下来，以后排期沿用。

执行规律保持简洁（约 15 行内），过时的更新而不是堆叠。

## 规划原则

- **目标必须可验证**：不接受"提升自己""多学习"这种无法判断完成的目标，必须先澄清。
- **关键路径优先**：先做阻塞后续的事，先验证最大的不确定性。
- **近细远粗**：只把本周细化到具体动作；远期只到里程碑，到了再细化。
- **任务可执行**：每个任务动词开头、≤ 半天能完成、有明确的完成标准（如"写完简历初稿并发给 1 个朋友看"，而不是"优化简历"）。
- **用数据说话**：估时和负荷以历史记录为准，不以用户的乐观预期为准。
- **宁少勿满**：能坚持的少量任务胜过排满后放弃；超载时让用户做取舍，而不是替用户硬塞。
- **反馈简短**：每次只提 1–2 个最重要的调整。

## 模板

### profile.md

```markdown
# 用户画像（更新于 YYYY-MM-DD）

## 精力
- 每周可投入：约 X 小时（自报）/ 实际约 Y 小时（近 4 周平均）
- 可用时段：工作日晚上 20:00–22:00，周六上午
- 精力高峰：早上
- 固定约束：……
- 偏好节奏：每天一点 / 周末集中

## 执行规律
- 估时系数：1.0（实际耗时 / 预估耗时，随记录更新）
- 容易完成：……
- 容易拖延：……
- 常见阻碍：……
- 有效策略：……
```

### `goals/<slug>.md`

```markdown
# 目标：[一句话目标]（v1，更新于 YYYY-MM-DD）

- 状态：进行中 / 暂停 / 已达成 / 已放弃
- 完成标准：[可验证的结果]
- 截止：YYYY-MM-DD
- 为什么：……
- 起点：……
- 约束：……
- 每周分配精力：约 X 小时

## 子目标
| # | 子目标 | 来源 | 优先级 | 依赖 | 预估投入 | 状态 |
|---|--------|------|--------|------|----------|------|
| 1 | …… | 用户 | P0 | - | 4h | 进行中 |
| 2 | …… | AI 补充：[理由] | P1 | 1 | 2h | 未开始 |

## 阶段里程碑
- [ ] M1（YYYY-MM-DD）：[可验证的阶段成果]
- [ ] M2（YYYY-MM-DD）：……

## 风险与待验证假设
- ……
```

### plan.md

```markdown
# 推进方案（v1，更新于 YYYY-MM-DD）

## 精力分配（每周可排 X 小时 = 可投入精力 × 80%）
| 目标 | 每周小时 | 说明 |
|------|----------|------|
| …… | …… | …… |

## 本周任务（YYYY-MM-DD ~ YYYY-MM-DD）
| 时间 | 任务 | 所属目标 | 优先级 | 预估 | 完成标准 | 状态 |
|------|------|----------|--------|------|----------|------|
| 周一晚 | …… | …… | P0 | 1.5h | …… | [ ] |

## 下次复盘：YYYY-MM-DD
```

### log.md 条目

```markdown
## YYYY-MM-DD（周X）[进度 / 启动 / 复盘 / 达成 / 更正]
- 目标：……
- 完成：[任务，实际耗时 vs 预估]
- 未完成：[任务及原因]
- 阻碍 / 感受：……
- 调整：[对方案做了什么改动，没有则省略]
```

## 示例

**新目标**

用户："想转行做 AI 产品经理。子目标：学 AI 基础、做个作品。每周大概 8 小时。"

处理：
1. 澄清缺失项，给具体化选项："怎么算转行成功？A. 半年内拿到 AI PM offer；B. 先在现公司内部转岗；C. 先接一个 AI 项目积累经验。截止时间？现在是什么岗位？"
2. 用户选 A、截止 2027-04、现为传统产品经理 → 保留"学 AI 基础""做作品"，补充：「AI 补充：先找 2–3 位 AI PM 聊聊岗位真实要求——最大的不确定性是作品方向是否对口」（P1）、「AI 补充：改简历 + 投递 + 面试准备——作品做完不等于拿到 offer」（P0，后期关键路径）。
3. 估算总需求约 180h，估时系数 1.0，每周可排 8 × 0.8 = 6.4h，半年约 166h → 缺口约 14h，给出选项：作品范围收窄 / 每周加 1h / 截止延到 5 月。
4. 用户选收窄作品范围 → 输出里程碑（M1 第 3 周：完成 3 次行业访谈；M2 第 10 周：作品上线……）和本周任务，写入文件。

**汇报进度**

用户："这周访谈只约到 1 个，花了 3 小时，原计划 1.5 小时。"

处理：log 顶部追加记录 → 子目标状态更新 → 本次耗时比值 2.0，估时系数 1.0 → 1.3，执行规律记下"需要联系他人的任务容易超时" → 反馈："访谈完成 1/3，下周把剩下 2 个约好并拆成「今晚发 5 条约聊消息」这种小动作；后续预估都按 1.3 倍算。"
